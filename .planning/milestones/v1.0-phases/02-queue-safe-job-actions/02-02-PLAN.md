  <action>
Create `pages/api/admin/enqueue-artists.js` as a POST-only admin endpoint.

**Method guard:** Return 405 `{ error: 'Method not allowed' }` for non-POST requests.

**Request body shape:** `{ artists: [{ spotifyId: string, name?: string }] }`
- Parse with `req.body.artists` — Next.js parses JSON bodies automatically.
- If `artists` is missing or not an array, return 400 `{ error: 'artists must be a non-empty array' }`.
- If `artists` is an empty array, return 400 `{ error: 'artists must be a non-empty array' }`.
- Max array length is NOT enforced in Phase 2 (no limit per CONTEXT.md).

**Database connection:** Call `connectDB()` (from `@/lib/mongodb`) at the top of the handler before any Mongoose operations. Match the pattern in other admin handlers.

**Per-item processing loop** (sequential `for...of` — NOT `Promise.all`, preserves input order per CONTEXT.md):

For each artist in `artists`:

Step 1 — Validate required field:
```javascript
if (!artist.spotifyId) {
  results.push({ artistSpotifyId: null, artistName: artist.name || null, status: 'failed', reason: 'missing_artist_id' });
  continue;
}
```

Step 2 — Within-payload deduplication (first occurrence wins, subsequent are skipped):
```javascript
if (seen.has(artist.spotifyId)) {
  results.push({ artistSpotifyId: artist.spotifyId, artistName: artist.name || null, status: 'skipped', reason: 'already_active' });
  continue;
}
seen.add(artist.spotifyId);
```
(`seen` is a `new Set()` initialized before the loop)

Step 3 — Atomic active-job check (QUEUE-02 idempotency guard):
```javascript
const existingActive = await ArtistJob.findOneAndUpdate(
  { artistSpotifyId: artist.spotifyId, status: { $in: ['queued', 'running'] } },
  { $set: { updatedAt: new Date() } },
  { new: false }
);
if (existingActive) {
  results.push({ artistSpotifyId: artist.spotifyId, artistName: artist.name || null, status: 'skipped', reason: 'already_active' });
  continue;
}
```

Step 4 — Redis enqueue FIRST (fail fast before persisting):
```javascript
const enqueued = await enqueueArtistExpand({
  artistSpotifyId: artist.spotifyId,
  artistName: artist.name || null,
});
if (!enqueued) {
  results.push({ artistSpotifyId: artist.spotifyId, artistName: artist.name || null, status: 'failed', reason: 'redis_unavailable' });
  continue;
}
```
IMPORTANT: Enqueue to Redis BEFORE writing queued status to MongoDB. This avoids orphaned `queued` records if Redis is down (Pitfall 5 from RESEARCH.md).

Step 5 — Upsert ArtistJob to queued state (only reached if Redis enqueue succeeded):
```javascript
try {
  await ArtistJob.findOneAndUpdate(
    { artistSpotifyId: artist.spotifyId, status: { $nin: ['queued', 'running'] } },
    {
      $set: { status: 'queued', queuedAt: new Date(), error: null },
      $setOnInsert: { artistName: artist.name || null },
    },
    { upsert: true, new: true }
  );
  results.push({ artistSpotifyId: artist.spotifyId, artistName: artist.name || null, status: 'queued', reason: 'queued' });
} catch (err) {
  if (err.code === 11000) {
    // Concurrent upsert race — another request won; treat as skipped
    results.push({ artistSpotifyId: artist.spotifyId, artistName: artist.name || null, status: 'skipped', reason: 'already_active' });
  } else {
    results.push({ artistSpotifyId: artist.spotifyId, artistName: artist.name || null, status: 'failed', reason: 'db_error' });
  }
}
```

**Summary computation** (after loop, before response):
```javascript
const summary = {
  total: results.length,
  queued: results.filter(r => r.status === 'queued').length,
  skipped: results.filter(r => r.status === 'skipped').length,
  failed: results.filter(r => r.status === 'failed').length,
};
```

**Response:** Always `res.status(200).json({ summary, results })` — HTTP 200 for mixed results per CONTEXT.md.

**Export:** `export default requireAdmin(handler)` — same pattern as access-check.js.

**Note on done status:** Allow re-enqueue of `done` artists (their record will be updated from `done` to `queued` by the upsert). A done artist has status `$nin: ['queued', 'running']` so the upsert matches and re-activates. This is per RESEARCH.md open question resolution.
